1.1 Core Architectural Principles
• Every module is self-contained: its own routes, services, repositories, and DB schema namespace.
• Modules communicate only through well-defined internal APIs (TypeScript interfaces) — never by importing
each other's database queries directly.
• Multi-tenancy is row-level: every table that holds tenant data has a tenant_id column. No separate schemas
per tenant.
• Feature flags control which modules a tenant (hotel) has purchased. Middleware enforces this on every
request.
• All financial calculations (pricing, commissions, payroll) happen server-side only — never in the browser.

5. MODULE SPECIFICATIONS
Each module follows the same file pattern: router.ts (tRPC) → service.ts (business logic) → repository.ts (Prisma
queries). Below are the required endpoints and business rules for each module.
5.1 Reservation Module
Key Business Rules
• When a reservation is created, automatically calculate totalPrice using: (multiplier × nights ×
pricePerNight) × (1 - agencyDiscount).
• If the room status is FAULTY or DIRTY, block check-in and show a warning.
• No-show and cancellation policies are defined per tenant in Settings. If a reservation passes the
no-show threshold, trigger a fee transaction automatically.
• Electronic signature: generate a unique link, send via WhatsApp/email/SMS. Store signed
document URL. Mark reservation as signed. If not signed digitally, staff can upload a scanned
copy.
• Jandarma KBS notification must be sent within the legally required time window after check-in. Use
a BullMQ delayed job.
• Guest history tab: aggregate all past reservations for this guest, total revenue, total profit (revenue
minus per-person cost), extra services cost.

5.2 Housekeeping Module
Key Business Rules
• Room approval (marking CLEAN) requires the minimum number of photos defined for that room
type. The system must reject approval if photo count is below the threshold.
• When a room is marked FAULTY from HK app, a FaultReport is automatically created in the
Maintenance module with location pre-filled.
• Cleaning duration is measured from task startedAt to completedAt. Include in HK report.
• Common areas have a cleaningFrequencyDays value. A scheduled BullMQ job runs daily at 06:00
and creates pending CommonAreaSchedule entries for any area whose last completion is older
than its frequency.
• Automatic HK report is generated at a tenant-configurable time (default 09:00) and sent by email to
the manager. Report includes: room statuses summary, tasks completed/pending, average
cleaning time, common area status.

5.4 Accounting Module
Key Business Rules
• All prices stored in Turkish Lira (TRY) as integers (kuruş / cents) to avoid floating point errors.
Display with /100.
• GIB integration: use an intermediary integration library (e.g. edonusum or similar). Never implement
raw GIB XML from scratch. The GIB envelope ID must be stored on every e-invoice.
• Warehouse stock is updated in a database transaction together with the invoice line items. Never
update stock without an invoice/transfer record.
• Department requests follow a strict status machine: PENDING → APPROVED (stock deducted) |
REJECTED | MODIFIED (quantity adjusted, then back to PENDING for re-approval).
• Every Transaction record must reference either an invoiceId, a reservationPaymentId, or a manual
entry reason. Orphaned transactions are not allowed.

5.6 Sales, Collections & Refunds Module
Key Business Rules
• Virtual POS: store encrypted POS credentials per tenant in Settings. Build a POS adapter interface
— each bank (Garanti, İşbank, Yapı Kredi, Akbank, etc.) implements the same interface. This
allows adding new banks without touching business logic.
• Payment link: generate a JWT-signed URL containing reservationId and amount. The link renders a
payment page that calls the tenant's virtual POS. Store result as ReservationPayment.
• Refund records must always store both guestRequestDate and refundProcessedDate separately.
• Guest marketing export: query all guests with email or phone for the tenant, format as CSV
compatible with Facebook Custom Audiences and Google Customer Match. Export only with
KVKK consent flag = true.
• Package products: a Package links multiple StockItems or services to a single sale price. When a
package is sold, individual components are deducted from stock.

5.7 Agency Contract & Pricing Module
Key Business Rules
• Price formula: finalPrice = multiplier(persons) × nights × pricePerNight(dateRange) × (1 -
agencyDiscount%). This formula must be the single source of truth — used in reservation creation,
price preview, and price audit report.
• Kickback auto-calculation: after each reservation payment is recorded, check if the agency's
cumulative confirmed revenue for the current season exceeds the kickbackThreshold. If yes, apply
kickbackRate to the excess amount and create a payable transaction.
• Price audit: for each reservation in a date range, recalculate the expected price using the formula
and compare to the stored totalPrice. Export result as Excel with columns: reservationId,
guestName, agency, storedPrice, expectedPrice, isCorrect(YES/NO), difference.
• All price changes are logged in AuditLog with the old and new value, timestamp, and userId.

5.8 CRM, Surveys & Guest Relations Module
Key Business Rules
• Checkout survey gate: when staff attempts to check out a reservation, the system checks if an
isCheckoutSurvey=true Survey exists for that reservationId. If not, the checkout is blocked and the
survey form is shown. This gate can be disabled per tenant in Settings.
• External review import: staff provides URLs for HolidayCheck, TripAdvisor, Google, etc. in Settings.
A background job scrapes or uses available APIs to pull reviews. If the platform reviewer name
does not match any guest, staff can manually link to a Guest record.
• Complaint book OCR: accept a photo upload, run through an OCR service (Azure Vision or
Tesseract), extract text, auto-detect language, translate to Turkish if foreign. Pre-fill complaint form
with extracted text. Staff can edit before saving.
• Guest birthday reminders: BullMQ job runs daily, finds guests with birthday tomorrow or today,
sends personalized message via SMS or email.
• Blacklist check: on every new reservation creation, check if the guest's tcId or passportNo is on the
tenant's blacklist. If yes, show a blocking warning with the reason.

6. MULTI-TENANCY IMPLEMENTATION
Concern Implementation
Tenant identification Every API request resolves tenantId from the Clerk organization ID. Helper:
lib/auth/getTenantId(clerkOrgId). Store in request context.
Data isolation All repository functions receive tenantId as the first argument and always
include WHERE tenantId = $1. No exceptions.
Module access control Middleware checks Tenant.activeModules before routing to any module
router. Return 403 if module not active for tenant.
Tenant onboarding When a new Clerk organization is created (webhook), create a Tenant row
with a default set of activeModules. Trigger a setup wizard on first login.
Tenant settings A Settings table stores per-tenant config (no-show policy, HK report time,
SGK rates, survey gate toggle, etc.). Always loaded into request context.
Super admin A separate SUPERADMIN role (Clerk metadata) can access all tenants for
support purposes. Build a /admin panel scoped to this role.

7. EXTERNAL INTEGRATIONS
7.1 GIB E-Invoice / E-Dispatch
• Use a Turkish e-invoice integration middleware library (do not implement raw GIB XML/SOAP).
• Implement an adapter pattern: GIBAdapter interface with methods: sendInvoice, getInboxInvoices, getStatus.
• Store gibEnvelopeId on every invoice. Poll status via BullMQ job every 30 minutes for pending invoices.
• Barcode scanning: accept input from a USB barcode reader (standard keyboard input on a focused input field).
On scan, look up StockItem by barcode and add to current invoice/request form.
7.2 Jandarma KBS (Identity Notification System)
• Integrate via the official e-Government API gateway or an approved intermediary service.
• Guest check-in notification: triggered as a BullMQ job 5 minutes after checkIn is recorded.
• Employee entry/exit: triggered immediately on shift start/end record.
• Store notification status and response code on each Reservation / Shift record.
• Failed notifications must be retried (max 3 times with exponential backoff) and logged.
7.3 Virtual POS (Sanal POS)
• Build a VirtualPOSAdapter interface: { charge(amount, cardToken, orderId), refund(transactionId, amount),
getStatus(orderId) }
• Implement one concrete adapter per bank. Start with at minimum: Garanti BBVA (Paycore), İşbank (Sanalpos),
Yapı Kredi (Posnet).
• Payment link flow: POST /api/payment/[token] renders a Next.js page with 3D Secure redirect. On callback,
update ReservationPayment record and redirect to success/fail page.
• Never store raw card numbers. Only store bank transaction IDs.
7.4 SMS / WhatsApp (Netgsm)
• Use Netgsm HTTP API for SMS. For WhatsApp, use Netgsm's WhatsApp Business API integration.
• All outbound messages go through a MessageService that queues via BullMQ (never send synchronously in a
request handler).
• Message templates: stored in DB per tenant (customizable). Variables: {guestName}, {checkInDate},
{signatureLink}, {paymentLink}, etc.
7.5 OCR for Complaint Book
• Use Azure Cognitive Services (Computer Vision Read API) or Google Vision API for photo-to-text.
• Language detection + translation: use Azure Translator or DeepL API.
• OCR result is always editable by staff before saving — it is a suggestion, not a final value.

11. CODING CONVENTIONS FOR CLAUDE CODE
Convention Rule
File naming kebab-case for files and folders. e.g. reservation-service.ts
Function naming camelCase. Service functions: verb + noun. e.g. createReservation,
calculatePrice
Error handling
Never use try/catch in route handlers. Use a global tRPC error formatter. Throw
TRPCError with appropriate code (BAD_REQUEST, NOT_FOUND,
FORBIDDEN).
Validation All input validated with Zod schemas defined in types.ts of each module. Share
schemas between client and server.
Money Always store as integer (kuruş). Never use float for money. Use a
formatCurrency(kuruş: number): string utility for display.
Dates Store all dates as UTC in PostgreSQL. Use Day.js for manipulation. Display in
Europe/Istanbul timezone.
Tenant context Every tRPC procedure must call ctx.requireTenant() at the top. This throws
UNAUTHORIZED if tenantId is missing.
Database queries All in repository.ts files. No raw SQL in service or router files. Use Prisma's
typed query builder.
Logging Use a structured logger (Pino). Log every mutation with tenantId, userId, action,
entityId. Never log PII (TC ID, passport, full name) in production logs.
Environment variables All secrets in .env.local (never committed). Documented in .env.example with
placeholder values.
Comments Write comments for why, not what. Business rule comments (e.g. // SGK rate
per 2024 regulation) are mandatory on all financial calculations.
Translations All user-facing strings in /messages/tr.json. Use next-intl. No hardcoded Turkish
text in component files.

## Project Overview
HotelOS is a multi-tenant SaaS hotel management platform built with Next.js 14
(App Router), TypeScript, Tailwind CSS, shadcn/ui, tRPC, Prisma, and PostgreSQL.
Authentication via Clerk (org-per-tenant). Background jobs via BullMQ + Redis.
Architecture: modular monolith designed for future microservice extraction.
Deployment: Vercel (frontend) + Railway (DB/workers).
## Architectural Rules (Non-Negotiable)
- All money stored as integers in kurus (TRY cents). Use formatCurrency() for display.
- All dates stored as UTC. Display in Europe/Istanbul timezone using Day.js.
- Every repository function receives tenantId as first arg. Always filter by it.
- Modules never import each other's repository files. Use module router interfaces only.
- All inputs validated with Zod. Schemas defined in module/types.ts, shared client+server.
- Every mutation logged to AuditLog via Prisma middleware (tenantId, userId, entity, diff).
- Never log PII (TC ID, passport, full name, card data) in production logs.
- Every tRPC procedure calls ctx.requireTenant() as first line.
- No raw SQL. Prisma query builder only in repository.ts files.
## Modules
1. Reservation — rooms, guests, bookings, check-in/out, e-signature
2. Housekeeping — room/area cleaning tasks, photos, checklists, lost & found
3. Maintenance — fault reports, equipment, preventive maintenance
4. F&B — menus, allergens, recipes, food cost, name tags
5. Accounting — stock, invoices (GIB), warehouse, payables, cash flow
6. HR — employees, shifts, leave, payroll, training
7. Sales — virtual POS, payment links, refunds, packages, campaigns
8. Agency — contracts, pricing calendar, multipliers, kickback, audit
9. CRM — surveys, reviews, complaints, blacklist, segmentation
10. Reporting — all 19 reports (screen + Excel/PDF export)
## Integrations
- GIB e-invoice/e-dispatch: adapter in lib/integrations/gib/
- Jandarma KBS: adapter in lib/integrations/jandarma/
- Virtual POS: VirtualPOSAdapter interface, one file per bank in lib/integrations/pos/
- Netgsm SMS/WhatsApp: adapter in lib/integrations/sms/
- OCR (complaint book): Azure Vision or Google Vision in lib/integrations/ocr/
